## Accounts
- Register: full name + phone (E.164, all countries, normalized/validated) + password + confirm. No email asked.
- Login: phone + password (email login removed). Google (Android only) / Apple (iOS only).
- Social first sign-up → mandatory phone screen + OTP before the account is usable.
- Uniqueness: phone unique (verified phones only own a number); identities table (provider, subject) unique → linked to one user; linking a social identity to an existing phone account only after that phone is verified via OTP by the same person.
- Passwords: argon2id (or existing bcrypt if argon2 unavailable — check), constant-time compare, rate limited.

## OTP engine (backend/app/domain/services/otp/)
- Purposes: signup, phone_change, new_device (new_device: NEVER SMS), password_reset (WhatsApp → SMS allowed? treat like signup).
- One challenge per operation: 6-digit code, hashed (HMAC-SHA256 with server key), TTL 5 min, single use, max 5 wrong attempts → locked; idempotency key from client; resend cool-down (30 s, then 60 s, 120 s), per-phone/per-IP/per-device/per-account hourly+daily caps.
- Channel orchestration (state machine, async worker or background tasks, persisted in DB so restarts are safe):
  1. WhatsApp template send (provider abstraction `MessageProvider` with WhatsAppCloudProvider, SmsToProvider; registry, easy to add more).
  2. Accepted (200 + wamid) ≠ delivered. Track statuses via webhook (sent/delivered/read/failed with error codes).
  3. Fallback to SMS only for signup/phone_change when: WhatsApp permanently failed (e.g. 131026 not on WhatsApp, 131049/131050, invalid number), or no 'delivered' within a deadline (e.g. 20–25 s) — with temporary errors retried within the window; never SMS twice per challenge (DB unique constraint / row lock); never SMS while a WhatsApp delivery is still reasonably likely.
  4. User can see channel status and tap "send via SMS" only when allowed by the same rules.
- Cost guard: per-message cost estimates (WhatsApp auth template rate per country, SMS.to price via its estimate API or table), daily/monthly budgets (env/admin-configurable) per channel and global; when exceeded → SMS disabled (WhatsApp still allowed within its own budget); metrics: sends, deliveries, failure reasons, SMS share, spend; admin endpoint/counts.
- Webhooks: GET verify (hub.challenge with WHATSAPP_VERIFY_TOKEN), POST with X-Hub-Signature-256 HMAC (app secret; configurable env META_WEBHOOK_APP_SECRET so the owner can supply the right app's secret), idempotent processing. SMS.to: per-message callback_url with a signed token (HMAC of message id) since SMS.to has no global secret; check docs.
- Real sends only in a dedicated manual test; unit tests mock providers.

## Trusted devices
- Device identity: on first launch each install creates an asymmetric key pair in Android Keystore / iOS Keychain (Secure Enclave when available; ECDSA P-256), never exported. Server stores the public key per device. Login/refresh proof = signature over a server nonce (challenge–response), not IP/location.
- First device that creates+verifies the account = primary (owner's main device). Trusted devices skip OTP while their key proof is valid and not revoked; network/IP/location changes never trigger OTP.
- New device + correct password → "verify this device" with two options only: (1) code to the primary device in-app (default, free), (2) WhatsApp. NO SMS for new-device login.
- Primary-device approval: server creates new_device challenge; pushes FCM data message WITHOUT the code ("login attempt"), plus in-app notification center row; the primary device fetches the code over its authenticated channel and shows a professional popup: device name/model, OS, approx location (from IP geolocation if available offline DB; else omit), date/time, 6-digit code, countdown, warning text «إذا لم تكن أنت من يحاول تسجيل الدخول، تجاهل هذه الرسالة ولا تشارك الرمز مع أي شخص». Lock-screen notification text never contains the code (Android VISIBILITY_PRIVATE/secret, iOS hidden preview). Code invalid after expiry or success.
- After success the new device becomes trusted. Devices page (settings): list, rename, revoke (kill sessions + trust; next login requires verification), primary badge, transfer primary.
- Existing 3-device limit (round 14) stays.
- Recovery when the primary device is lost: from a new device, WhatsApp OTP on the account phone + password → device becomes trusted; to become primary, require a waiting period (e.g. 24–72 h) during which the old primary (if it comes online) can cancel; revocation of offline devices is enforced when they next come online (their key proofs are rejected). Document limits (offline devices keep local data until they reconnect).

## API contract v2 (prefix /api/v1/auth2 — old /auth stays only for refresh/logout/me/sessions/avatars until the client fully moves; email routes are disabled)
All bodies JSON; errors `{detail:{code, message_ar, message_en, retry_after?}}`. Every device request carries headers `X-Device-Id` (uuid per install) and, after enrollment, proof headers for /auth2/device/* as described.
Device key: ECDSA P-256 (Android Keystore / iOS Keychain-Secure Enclave). Public key sent as base64 SubjectPublicKeyInfo DER. Signatures: base64 DER ECDSA over UTF-8 `"fyona-device-proof|{nonce}|{device_id}|{purpose}"`.

- POST /auth2/device/nonce {device_id} → {nonce, expires_in}  (60 s, single use)
- POST /auth2/register/start {full_name, phone_e164, password, device:{id, public_key, name, model, os, os_version, app_version}, idempotency_key} → {challenge_id, channel:'whatsapp'|'sms', status, resend_after, expires_in}
- POST /auth2/otp/status {challenge_id} → {status:'queued'|'sent'|'delivered'|'read'|'failed'|'fallback_sms'|'verified'|'expired'|'locked', channel, can_request_sms:bool, resend_after}
- POST /auth2/otp/resend {challenge_id, channel?: 'whatsapp'|'sms'|'device'} → same as start (server enforces rules; 'sms' refused for new_device)
- POST /auth2/register/verify {challenge_id, code, nonce, signature} → AuthResponse (tokens + user; device becomes primary+trusted)
- POST /auth2/login {phone_e164, password, device:{...}, nonce?, signature?} →
    · trusted device with valid proof → AuthResponse
    · otherwise → 202 {needs_verification:true, verification_id, options:['device','whatsapp'], primary_device:{name, model}}
- POST /auth2/login/verify/start {verification_id, channel:'device'|'whatsapp'} → {challenge_id, channel, status, resend_after, expires_in}
- POST /auth2/login/verify {challenge_id, code, nonce, signature} → AuthResponse (device trusted)
- POST /auth2/social {provider:'google'|'apple', id_token, authorization_code?, nonce?, full_name?, device:{...}, signature?} →
    · existing linked + trusted device → AuthResponse
    · existing linked + new device → 202 needs_verification (as login)
    · new identity → 200 {needs_phone:true, social_session} (short-lived signed token)
- POST /auth2/social/phone/start {social_session, phone_e164, idempotency_key} → OTP start response (purpose signup; if the phone already belongs to an account → 409 code 'phone_taken' with hint to log in with password then link)
- POST /auth2/social/phone/verify {challenge_id, code, nonce, signature} → AuthResponse (account created, identity linked, device primary)
- POST /auth2/refresh {refresh_token, device_id, nonce, signature} → tokens (refresh bound to device key; revoked device → 401 code 'device_revoked')
- Primary device approval (authenticated, from the primary or any trusted device):
    · GET /auth2/approvals/pending → [{approval_id, device:{name, model, os, os_version}, location_hint, created_at, expires_at}]
    · POST /auth2/approvals/{approval_id}/code {nonce, signature} → {code, expires_at}  (code only to a trusted device with a fresh proof)
    · POST /auth2/approvals/{approval_id}/deny
  FCM data push type 'login_approval' {approval_id} (no code in payload; notification text generic); in-app notifications row with route '/security/approvals?id=…'.
- Devices: GET /auth2/devices → [{device_id, name, model, os, os_version, app_version, is_primary, trusted, last_seen, created_at, current}], POST /auth2/devices/{id}/revoke, POST /auth2/devices/{id}/rename {name}, POST /auth2/devices/{id}/make-primary {nonce, signature} (from current primary only).
- Phone change: POST /auth2/phone/change/start {new_phone_e164, password?, nonce, signature, idempotency_key} → OTP start (to NEW number; 409 'phone_taken'), POST /auth2/phone/change/verify {challenge_id, code} → {user}
- Password reset: POST /auth2/password/forgot {phone_e164, device:{...}} → OTP start (whatsapp→sms), POST /auth2/password/reset {challenge_id, code, new_password} → AuthResponse/ok
- Recovery (primary lost): login from new device → verification options include 'whatsapp' (always) → device trusted; POST /auth2/devices/claim-primary → starts a 48 h pending transfer (cancellable by the old primary: POST /auth2/devices/claim-primary/cancel), applied by a worker.
- Webhooks: GET/POST /api/v1/webhooks/whatsapp ; POST /api/v1/webhooks/smsto/{token}
- Admin (platform admin): GET /auth2/admin/otp-metrics (counts, delivery rates, spend vs budgets), PUT /auth2/admin/otp-budgets.
AuthResponse = existing shape (access_token, refresh_token, token_type, user, session_id) + device:{device_id, is_primary, trusted}.

### Proof purposes (client side, v2 — the `{purpose}` field of the signed string)
The client always fetches a fresh nonce (`POST /auth2/device/nonce`) right before a signed call and uses exactly these purposes:
`register_verify` (/register/verify) · `login` (/login, always sent; server may ignore for unknown devices) · `login_verify` (/login/verify) · `social` (/social) · `social_phone_verify` (/social/phone/verify) · `refresh` (/refresh) · `approval_code` (/approvals/{id}/code) · `make_primary` (/devices/{id}/make-primary) · `phone_change` (/phone/change/start).
Device object sent everywhere: `{id, public_key, name, model, os, os_version, app_version}`; every request also carries header `X-Device-Id`.
Client field notes (v2): `/auth2/social` → `nonce`/`signature` are the DEVICE proof (purpose `social`); Apple additionally sends `raw_nonce` = the raw random string whose SHA-256 hex Apple put in the identity token's `nonce` claim (server checks `sha256(raw_nonce) == claims.nonce`). `/auth2/devices` rows may carry `primary_claim_until` (ISO, on the device with a pending claim); `/auth2/devices/claim-primary` answers `{applies_at}`. Responses may be bare JSON or wrapped `{success, data}` (both accepted). `needs_verification` options from the server are filtered client-side to `device|whatsapp` (never SMS).

### Server notes (backend v2, implemented)
- Error envelope: HTTP status + `{success:false, detail:{code, message_ar, message_en, retry_after?, …}, message}` (`message` = message_ar for old clients); 429s also send `Retry-After`. Codes: `invalid_phone, weak_password, invalid_name, invalid_device, invalid_device_proof(401), invalid_nonce(401), invalid_credentials(401/429), account_inactive(403), account_not_found(404), phone_taken(409, hint 'login'|'login_then_link'), same_phone, device_limit(409, limit), device_not_trusted(403), device_revoked(401/403), verification_expired(401), invalid_social_token(401), social_token_expired, social_nonce_mismatch, jwks_unavailable(503), identity_linked(409), not_primary(403), cannot_revoke_primary(409), already_primary, device_not_found, approval_not_found, transfer_not_found, reauth_required(401), gone(410)` and OTP: `otp_rate_limited(429), otp_cooldown(429), otp_resend_limit(429), otp_unavailable(503), otp_not_found(404), otp_expired(410), otp_locked(423), otp_invalid_code(400, attempts_left), otp_already_used(409), otp_denied(403), sms_not_allowed(409), channel_not_allowed, idempotency_conflict(409)`.
- Legacy `/auth/register|verify-registration|resend-otp|login|forgot-password|verify-otp|reset-password|email-change-*|firebase` → 410 `gone` (env `AUTH_LEGACY_EMAIL_ROUTES` re-enables: QA lab sets `login` for seeded fake users). `/auth/refresh|logout|me|sessions|avatars|change-password` unchanged. User JSON gains `phone_verified`; `email` is `""` for phone-only accounts.
- OTP start/resend responses: `{challenge_id, channel, status, resend_after, expires_in, can_request_sms}`; `/otp/status` adds `attempts_left`. Poll `/otp/status` every 2–3 s (relaxed rate bucket). Timings: TTL 300 s (a resend issues a NEW code with a fresh TTL), resend cool-downs 30/60/120 s, max 3 resends, 5 wrong codes → `locked`. `can_request_sms` is true only for signup/phone_change/password_reset, when WhatsApp failed permanently or no delivery receipt within 25 s of acceptance, SMS not yet used, SMS budget left; `resend {channel:'sms'}` resends the SAME code by SMS (once per challenge). Automatic SMS fallback at 25 s is on only when the webhook secret is configured. `fallback_sms` means the SMS is being/was sent; its delivery receipt moves status to `delivered`.
- `/login` 202 also returns `expires_in` (600 s); `options` is `['device','whatsapp']` only if another trusted device exists, else `['whatsapp']`; `primary_device` may be null. `/login/verify/start` is idempotent per (verification_id, channel). For channel `device` the push goes to all the user's FCM tokens; codes are shown only via `/approvals/{id}/code` (proof `approval_code`, any trusted device except the requester); fetching marks the challenge `delivered`; deny → status `failed`.
- `/social`: `nonce` (server nonce) is consumed when sent; Apple requires `raw_nonce` (sha256 hex in the token) or, if absent, sha256(`nonce`). New identity → `{needs_phone, social_session (15 min), name_required, expires_in}`; `/social/phone/start` also accepts `full_name` (required when `name_required`). Apple `authorization_code` is exchanged server-side (refresh token kept encrypted, revoked on account deletion).
- Extra endpoints: `POST /auth2/social/link {provider, id_token, authorization_code?, nonce?, raw_nonce?}` (authenticated trusted device; links Google/Apple to the phone account) → `{linked, provider}`; `GET /auth2/devices/claim-primary` → `{pending:{transfer_id, from_device_id, to_device_id, status, apply_at, created_at}|null}`; `POST /auth2/devices/claim-primary` → `{pending, applies_at}`; `POST /auth2/account/delete {password?, nonce, signature}` (proof purpose `account_delete`; password required when the account has one) → `{ok}`.
- `/devices` rows also carry `revoked` and `primary_claim_until`. Authenticated `/auth2/*` device calls require header `X-Device-Id` equal to the session's device (the device the tokens were issued to). Revoke: primary revokes others, any device revokes itself, primary cannot be revoked; revocation kills that device's sessions + trust. Rename: self or primary. `/phone/change/start`: password OR proof `phone_change` (at least one); `/phone/change/verify` → `{user}`. `/password/forgot` → 404 `account_not_found` for unknown numbers; `/password/reset` → `{ok, message_ar, message_en}` and signs out every session (devices stay trusted). `/refresh` → `{access_token, refresh_token, token_type, device}`.
