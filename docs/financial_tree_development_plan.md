# خطة تطويرية — الشجرة المالية (Financial Tree)

> الوثيقة تصف الوضع الحالي، مشاكله المنطقية وUX/UI، ثم خارطة طريق مرحلية للوصول بها إلى مستوى Production-Ready احترافي.
> المرجع: `lib/features/personal/` (models, storage, provider, page, list_page, report_pdf).

---

## 1) تقييم الوضع الحالي (من الكود)

### الإمكانيات الموجودة فعليًا
- **النموذج**: `FinancialTree` (اسم، عميل، مبلغ أساسي، عملة، ملاحظات) + `FinancialTreeNode` (12 نوعًا) + `NodePayment` (أقساط/دفعات بحالة paid/pending/overdue) + `TreeComputation` + `FinancialTreeReportSnapshot` (لقطة للتقرير).
- **الحسابات**: `computeTree` يجمع `baseBalance, allocated, available, totalAssets/Income/Expenses/Investments/Receivable/Payable, netWorth, totalPaid, totalRemaining, distribution`.
- **التفاعل**: إضافة/تعديل/حذف عقد، دفع، إعادة ترتيب، نقل عقد لأب آخر (`moveNode` مع منع الدورات)، طي/توسيع، بحث، تكبير/تصغير canvas، رسوم بيانية (fl_chart)، تصدير PDF مع خيارات شاملة، سجل تقارير.
- **التخزين**: محلي بالكامل عبر SharedPreferences.

### نقاط القوة
1. بنية البيانات الأساسية سليمة كشجرة (parent/children/sortOrder).
2. منع الدورات عند النقل موجود.
3. تصدير PDF فعلي بـ RTL وCairo، مع لقطات (snapshot) غير قابلة للتغيير.
4. دعم عملات متعددة وتحويل عبر CurrencyEngine.

## 2) المشاكل المنطقية (لماذا "غير منطقية")

| # | المشكلة | الأثر |
|---|---------|-------|
| L1 | **المحاسبة خاطئة (Double counting)**: `netWorth = base + assets + investments + income + receivable − expenses − payable`. شراء سيارة 300K من نقد 1M يُحسب `netWorth = 1.3M` — مالٍ لم يُنفق! لا يوجد نموذج "تدفق نقدي"، فالأصل/الدخل يُجمعان بجانب النقد دون خصم النقد المدفوع. | أرقام مضللة → فقدان الثقة. |
| L2 | **لا يوجد تمييز بين المعنى المالي للعقد**: الأصل "يملك"، الدخل "تدفق وارد"، المصروف "تدفق صادر"، الدَين "التزام". الخوارزمية تتعامل معها كأرقام مضافة/مطروحة فقط دون فهم "المكان" المالي (ميزانية أم تدفق). | لا يمكن بناء ميزانية أو Cash Flow سليمة. |
| L3 | **Over-allocation غير مُراقب**: مجموع الأبناء قد يتجاوز المبلغ الأصلي للأب دون تحذير (`available` يتحول لسالب صامت). | أرقام سالبة غامضة. |
| L4 | **`distribution` خلط غير متجانس**: فطيرة تجمع أصول + دخل + مصروف + دَين معًا. | رسم بياني مضلل. |
| L5 | **`totalPaid` / `totalRemaining` خلط سيمانتيكي**: دفعات السيارات (شراء أصل) تُجمع مع دفعات الديون — معنى مختلف تمامًا. | تقارير غير مفهومة. |
| L6 | **لا زمن**: لا يوجد شهر/فترة، لا تدفقات زمنية، لا P&L، لا تطور للصافي عبر الوقت. | أداة "لحظية" بلا تاريخ. |
| L7 | **اختيار الجذر عشوائي**: `computeTree` يأخذ `first root`؛ التطبيق لا يمنع جذورًا متعددة أو عقدًا بدون أب. | حالات هامشية تكسر الحسابات. |
| L8 | **مزج عملات بصمت**: تُخزَّن المبالغ بعملة كل عقد وتُحوَّل لحظة العرض؛ إذا غاب سعر الصرف يعود المبلغ كما هو بلا تنبيه. | أرقام خاطئة عند فقدان سعر صرف. |

## 5) الرؤية

تحويل "الشجرة المالية" من **خريطة تنظيمية ملونة** إلى **أداة إدارة ثروة احترافية**:

> **مفهوم**: الجذر = النقد/المركز الافتتاحي (Cash & Opening Balance). الأبناء يُصنَّفون في **فئات مالية معتمدة** بعلامات حسابية صحيحة: أصل (يزيد القيمة)، استثمار، دخل (تدفق وارد)، مصروف (تدفق صادر)، دَين/التزام (يقلل الصافي)، مستحق قبض (يزيد)، دفعات (حركة نقدية فعلية).
> **الحساب**: ميزانية (Balance Sheet) + تدفق نقدي (Cash Flow) + صافي ثروة حقيقي بدون مضاعفة، مع تنبيهات Over-allocation و Over-payment.
> **التجربة**: لوحة لوحة تحكم مالية (KPIs + رسوم تفاعلية) + شجرة تلقائية التخطيط أنيقة بـ RTL وحركات سلسة + إدخال موجَّه بحسب نوع العقد.

## 7) مقاييس النجاح (DoD لكل مرحلة)
- `dart analyze lib` → 0 errors (الحالي: 0).
- `flutter test` → اختبارات المحرك + الواجهة كلها خضراء.
- **حسابيًا**: سيناريو "١,٠٠٠,٠٠٠ → سيارة ٣٠٠,٠٠٠ → ١٠٠,٠٠٠ دَين بأقساط ٢×٥٠,٠٠٠" يعطي:
  - صافي ثروة = نقد(٦٠٠,٠٠٠) + سيارة(٣٠٠,٠٠٠) − دين متبقي(٥٠,٠٠٠) = **٨٥٠,٠٠٠** (وليس ١.٣٪ مليون).
  - `freeCash = ٦٠٠,٠٠٠`, `cashOut = ٥٠,٠٠٠`.
- **تجربة**: كل إجراء (إنشاء/تعديل/سحب/دفع/تقرير) ≤ ٣ خطوات مرئية، وكل أخطاء مدخلات تظهر inline.
- **أداء**: شجرة ٥٠٠ عقد → إدخال/تحرير بلا تأخير ملحوظ (إعادة تخطيط محسوبة مرة واحدة لا لكل rebuild).
